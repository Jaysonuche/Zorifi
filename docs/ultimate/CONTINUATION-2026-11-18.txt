MP4 DIAGNOSIS AND REPAIR
The former export implementation used a MediaRecorder start event as frame
readiness and as the timeline clock. A premature requestData flush could emit
that event without encoded video. Conversely, waiting for the first muxed chunk
without that flush extended a real requested1.2s scene to2.171533s. Empty/audio-
only recordings were rejected correctly, but retrying did not repair capture.

Current app.js verifies an actual canvas video frame via a muted video-only
capture sink before recording, keeps the capture consumer active, requests each rendered frame explicitly where
supported, and uses the recorder.start call as the clock origin. MP4 gathers a
complete session without early/timed fragment flushes. It verifies real encoded
frames from a short local sample, negotiates supported H.264/AAC candidates, then
creates a fresh video capture and audio-track clone for the actual saved range.
The discarded sample never becomes a download or an edit/history checkpoint. Compatible automatic
capture and loadeddata fallbacks remain for browsers without those frame APIs.
Audio/video decoders are warmed together before recording; playback does not
block the frame loop. New source seeks are awaited after setting their target.
The sink, callbacks, timer, audio context and tracks are cleaned up on success,
failure and cancellation. Encoder errors stay visible; invalid outputs remain
blocked. An MP4 constructor failure no longer silently creates another format.
The existing explicit WebM alternative remains available after supported errors.

Diagnosis was iterative: isolated early-flush tests alone did not reproduce the
app failure. A first preflight/clock-only candidate passed some Edge cases but
failed delayed Chrome capture with audio-only output. Explicit per-paint capture
was then added. Cold codec probes and a separate fresh recording stream repaired
additional Chrome startup/first-frame failures; constructor support alone is
not treated as proof. An experimental frame-generator path did not fix those
failures and was removed. A multi-source regression also exposed sequential play-start
stalls; concurrent decoder warmup/nonblocking playback repaired that path. Only the final candidate's actual receipts count as current
verification. Diagnostic source bytes are real encoders, not fabricated MP4s.

NATIVE DRUM STEP SEQUENCER
Added16/32/64 evenly divided steps per actual source bar in native kick/snare/hat
patterns. Meter, BPM, bar, MIDI pitch and hit velocity remain real note data;
other bars, other pitches and off-grid notes are preserved. Partial last bars
disable cells beyond the source. Locks, resource limits and validation apply.
The same music.native.edit operation serves manual controls and reviewed Vanessa
commands, rerenders real WAV audio, saves one native Undo, and persists locally.
Example: Enable native drum step5 of32 in bar2 at pitch38 to70% velocity.
Responsive controls use the existing note dialog rather than a separate store.
Flam/roll/probability/chaining, full per-step pitch offsets, MIDI recording/MPE
and interactive piano-roll drawing remain incomplete. No world-first claim.
