ARCHITECTURE FOUND AND PRESERVED
- Frontend: vanilla index.html/app.js plus existing zorifi-* modules. There is
  one native editor state, not a second OpenAI-specific timeline/store.
- Authentication: zorifi-firebase.js FirebaseGateway. Backend provider.mjs
  verifiedAccount checks bearer ID tokens using Firebase accounts:lookup,
  rejects disabled/invalid accounts, and shares verification within one request.
- Routing: api/vanessa/chat.js and api/vanessa-provider.js adapt HTTP to
  netlify/functions/_shared/vanessa-router.mjs and services.mjs. Local routing
  is scripts/dev-server.cjs. Both existing hosting adapters remain available.
- Sessions: chat-session-store.mjs has per-UID Firestore sessions, ordered turns,
  pending locks, request hashes, HMAC-signed replay, and a 20-request/minute quota.
- Editing: zorifi-timeline-edit-api.js supplies actual split/trim/move/place/
  delete. zorifi-vanessa-professional-tools.js validates native action schemas.
  professional-planner.mjs validates source bounds, locks, dependencies, actual
  supported tools and motion graph operations. Client ProductionBridge/
  ProfessionalStudio handle review, commit verification, Undo/Redo and saving.
- Projects remain account-scoped device metadata and IndexedDB media. Backend
  receives supplied context/evidence, not access to another account's device.
  A supplied ownerUid must match Firebase identity; no new cloud project store
  is fabricated. Shared cloud records are namespaced by verified Firebase UID.

COMPLETED OPENAI INTEGRATION
1. openai-responses.mjs uses the OpenAI Responses API at a fixed HTTPS origin.
   OPENAI_API_KEY is read only on the backend. Redirects are disallowed, input/
   response sizes and output tokens are bounded, cancellation propagates,
   provider error bodies are never returned/logged, and no automatic paid retry
   is performed. Incomplete/refused/malformed output cannot become a valid edit.
2. Structured JSON output uses text.format json_schema with strict schemas.
   Optional values are represented compatibly and normalized before native
   validation. Models cannot send arbitrary mutations or executable code.
3. Vanessa chat/editing uses the existing authenticated /api/vanessa/chat route.
   Professional OpenAI plans use the same server tool catalogue and validators,
   then the same native client execution path. parametersJson is parsed as data
   and validated; it is never evaluated. History and source references remain.
4. vanessa-prompts.mjs stores versioned backend prompts for personality, ordinary
   conversation, editing, professional planning, Realtime and retrieval. No
   hosted prompt-management permission or remote prompt ID is required.
5. Locally, a configured OPENAI_API_KEY permits auto selection of OpenAI.
   Hosted auto selection preserves Gemini until OPENAI_HOSTED_ENABLED=true.
   VANESSA_LANGUAGE_PROVIDER explicitly selects openai/gemini/openrouter/auto.
   Existing Gemini image/music/speech and native device voice features remain.
   Existing legacy provider-specific keys remain supported by their old paths.
6. OpenAI professional planning consumes validated sampled images and measured
   metadata. Audio excerpts are explicitly omitted from this text/vision route;
   it does not claim to hear recordings. Maximum 32 sampled images per request.
7. OpenAI text over the existing SSE interface is currently buffered into a
   complete response. Token-by-token OpenAI streaming is not implemented.

AUTHORIZATION, RATE LIMITING AND USAGE
- Existing private Firestore chat quota and ordered session handling remain.
- openai-runtime.mjs binds provider calls to the authenticated request with
  AsyncLocalStorage. Additional per-account rate and daily allowance reservations
  occur before upstream requests; errors/cancellation retain honest receipts.
- Provider-reported input/output/total tokens and response/model identifiers are
  retained. Missing usage remains unknown; it is not reported as zero or as an
  invoice. Failed/incomplete responses with reported usage retain that usage.
- Hosted/serverless runtime uses OpenAIFirestoreState. Firestore records contain
  signed usage and opaque resource mappings, not project media or API keys.
  HMAC binds record contents, account, path and monotonic version. Compare-and-set
  writes protect concurrent requests. Replayed/forged state fails closed before
  another OpenAI request. A tampered account record requires operator repair.
- The added firestore.rules block permits only the owning account to read/write
  the bounded versioned record; no list/delete or other-user access. The backend
  validates signatures before trusting data. These rules were emulator-tested
  only and have NOT been published to the real Firebase project.
- A server-private SQLite alternative is available for local/stateful Node use.
  Its transactions and UID-scoped resource mappings persist across reopen.
  SQLite requires Node 22+ with node:sqlite support; this environment is Node 24.
  Serverless hosts never use temporary SQLite storage as a durable quota store.
- Production policy and all current limits are documented in
  docs/OPENAI-PRODUCTION-READINESS.txt, which supersedes this phase-one report.
- Defaults:20 OpenAI requests/minute/account and50000 daily allowance units.
  Chat's existing Firestore quota also caps 20 requests/minute. Allowances reserve
  conservative estimated tokens; image/video/audio charges are not accurately
  represented by token counts. This is NOT a guaranteed monetary spending cap.
  Check the OpenAI project's actual billing/limits. Firestore retains a bounded
  rolling ledger (512 requests/24h and 128 resource mappings per account).
- Hosted OpenAI now requires a stable OPENAI_STATE_SIGNING_KEY of32+ characters.
  Local development also supports VANESSA_SESSION_SIGNING_KEY. Local fallback
  signs with OPENAI_API_KEY; rotating that key without a stable signing secret
  invalidates previous signed state and requires explicit operator recovery.

PREPARED OPTIONAL CAPABILITIES — MOCK-TESTED BACKEND ADAPTERS
Canonical local/Vercel endpoint: POST /api/vanessa/openai.
Netlify function: /.netlify/functions/vanessa-openai.
Every request uses Firebase authentication. Optional capabilities additionally
require their environment flag, an allowed exact Firebase UID, and consent:true.
All flags default off; configuring a key does not automatically enable them.

Resource requests accept opaque account-scoped handles, not arbitrary provider
file/vector/video IDs. No organization-wide resource listing, arbitrary URL
proxy, remote filesystem access or automatic project upload was introduced.
Retrieved text is untrusted evidence, never executable instructions.

  provider job already accepted. No fake generation progress/success is returned.
- No new claims of professional creative quality, physical-device microphone
  behavior or universal format/model support are made from mock tests.

EXACT LOCAL KEY ENTRY / ONE LIVE CONNECTION TEST
Run these in ordinary PowerShell terminals at the repository root. Do not type
the key as a command argument, paste it in chat, or save it in an env/source file.

Terminal1:
  npm run openai:emulators

Terminal2:
  .\scripts\Start-ZorifiOpenAI.ps1 -Mode LiveTest

The PowerShell script calls Read-Host -AsSecureString. Type the key into that
hidden prompt. It converts it in memory, passes OPENAI_API_KEY through the child
process environment, and clears the added environment value and BSTR afterward.
It never writes the key to disk, command history, stdout, a command argument,
the browser, logs, or Git. Normal OS administrators can inspect process memory;
environment secrets are not protection against a compromised local machine.

LiveTest creates a disposable local Auth emulator account, verifies it through
the actual backend, and requests only a public fixed connection phrase from
Responses. It prints sanitized status/model/response ID/token usage and exits.
The test can consume OpenAI API credits, but provisions no Firebase paid service.
Other modality flags stay off. A200 connected:true verifies only that connection
and chosen model; it does not verify the optional media/Realtime/retrieval paths.

For a local UI using mocked AI, no key is needed:
  npm run openai:emulators
  npm run openai:mock
  Open http://127.0.0.1:4175 and sign up with a disposable demo account.
For an explicitly live local UI, use -Mode LiveServer instead of -Mode LiveTest.

LOCAL TOOLING
The emulator helper reuses the isolated cached firebase-tools 14.24.2 CLI and the
available local Java 21 JRE. If the CLI is missing:
  npm exec --yes --package=firebase-tools@14.24.2 -- firebase --version
On another machine, install Java 21 and set JAVA_HOME; or set FIREBASE_CLI_PATH to
an installed firebase-tools/lib/bin/firebase.js. No app runtime dependency was
added just to run emulators. Emulator mode requires a loopback demo-* project
and is rejected on production hosts or for a real Firebase project.
